# 工作便签提醒 · 三端共享契约（数据模型 + 备份格式 v1）

路线 A 的约定：Android / 鸿蒙 Next / iOS 三套**独立原生工程**，互不共享代码，只共享两样东西——**数据模型**和**备份文件格式**。换机、跨端迁移都只靠 `.taskbak` 这一份 JSON。

本文是三端的唯一事实来源。任何一端改动字段、语义或导入规则，必须同步改这里，否则三端会静默不兼容（不报错，但数据会丢）。

---

## 一、字段表（`.taskbak` 里的 `notes[]` 每一条）

| 字段 | 类型 | 必填 | 含义 | 缺省值 | 承载方 |
| ---- | ---- | ---- | ---- | ---- | ---- |
| `title` | string 1–60 | 是 | 标题，列表单行显示 | `未命名便签` | 全部 |
| `remark` | string 0–500 | 否 | 备注，可为空串 | `""` | 全部 |
| `dateKey` | string `yyyy-MM-dd` | 是 | 归属日期，日程页按它分组 | 当天 | 全部 |
| `remindAt` | int64 毫秒 | 是 | 提醒的**绝对时刻**，`0` = 不设定时 | `0` | 全部 |
| `loopType` | enum | 是 | `NONE` / `DAILY` / `WEEKLY` / `MONTHLY` | `NONE` | 全部 |
| `repeatEnabled` | bool | 否 | 没处理时是否隔一会儿再催 | `false` | 全部 |
| `repeatMinutes` | int 1–1440 | 否 | 再催间隔（分钟） | `15` | 全部 |
| `status` | enum | 是 | 见下方状态机 | `PENDING` | 全部 |
| `createdAt` | int64 毫秒 | 是 | 创建时刻 | 导入时刻 | 全部 |
| `remindCount` | int ≥0 | 否 | 被强提醒弹过几次 | `0` | 全部 |
| `actions[]` | array ≤4 | 否 | 强提醒卡片上的自定义按钮 | `[]` | 全部 |
| `actions[].text` | string 1–12 | 是 | 按钮文字 | — | 全部 |
| `actions[].type` | enum | 是 | `DONE` 完成 / `DELAY` 延后 / `CLOSE` 只关卡片 | `DONE` | 全部 |

**故意不写的两个字段**：
- `id`：各端本地主键各自生成（Android 是 `INTEGER PRIMARY KEY AUTOINCREMENT`），跨端传递没有意义，还会导致主键冲突。
- `updatedAt`：导入重建时由各端重新写，写进文件只会带来"导入后时间倒流"的困惑。

> 校验工具会拒绝超过长度上限的值。上限是按 Android 现有录入界面定的：标题单行、按钮一行放得下。放宽之前先改这里。

## 二、状态机（三端必须一致）

```
PENDING（待提醒）
   ↓ 到点弹了强提醒但没处理
READY（待处理）
   ↓ 点「延后」
POSTPONED（已延后）—— 到点后再回到 READY
   ↓ 点「完成」
DONE（已处理）
   ↓ 用户归档
ARCHIVED（已归档）

任意状态 → DELETED（回收站，可从回收站恢复）
```

- **能弹强提醒的只有 `PENDING` / `READY` / `POSTPONED`**（Android 里对应 `Note.isActive`）。
- `DONE` / `ARCHIVED` / `DELETED` 一律不再排提醒。

## 三、时间语义（跨端最容易搞错的地方）

- `remindAt` 是**绝对时刻**（Unix 毫秒），不是"今天几点"。用户飞到别的时区，这条提醒的绝对时刻不变，但本地显示的钟点会变。
- `dateKey` 是**本地日历日**，只用于日程页分组，不参与计时。
- 两者可能打架：用户换时区后，`dateKey` 还是那天，`remindAt` 已经落到别的日子。**规则是：以 `remindAt` 为准重排提醒，`dateKey` 不自动改**——因为随手改用户的归属日期比留一条"提醒跑偏"更糟。
- 循环（`DAILY` / `WEEKLY` / `MONTHLY`）一律按**本地日历**推下一跳。`MONTHLY` 遇到 31 号在小月不存在时，落到该月最后一天（不跳过、不顺延到下月）。

## 四、导入规则（三端必须完全照抄，否则换机会丢东西）

1. **整体替换**，不是合并。导入前必须弹确认：会覆盖本机现有全部便签。
2. `status`：`DELETED` 保持 `DELETED`（进回收站），**其余一律回落 `PENDING`**。原因：`READY` / `POSTPONED` 是"系统正在调度"的中间态，换了设备调度表已经不存在，硬保留会让提醒永久不响。
3. `remindCount` 一律重置 `0`。
4. `id` / `updatedAt` 由本端重新生成。
5. 导入后**必须重排全部提醒**（iOS 重新登记本地通知，鸿蒙重排 `reminderAgent`，Android 重排 `AlarmManager`）。系统调度表不跟文件走。
6. 未知字段忽略不报错（为将来加字段留退路）；缺字段按第一节缺省值补。
7. 空 `notes` 数组视为非法备份，直接报错不导入。

| 循环 | `loop_type` / `loopType` | `loopType` | `loopType` | `loopType` |
| 再催开关 | `repeat_enabled` / `repeatEnabled` | `repeatEnabled` | `repeatEnabled` | `repeatEnabled` |

## 六、校验工具（三端 CI 共用）

```
python contract/validate_backup.py <文件.taskbak>      # 校验单个文件
python contract/validate_backup.py --all <目录>        # 校验一批
python contract/android_db_to_taskbak.py <db> <out>    # 把 Android 库转成备份，做联调
```

退出码 `0` 通过、`1` 不通过。校验内容包括：字段类型、枚举、长度上限、`dateKey` 是否为真实日期、时间戳是否在 2000–2100 之间、重复条目、以及**按第四节规则预演导入结果**（三端导入后必须长得一模一样）。

自测样本：
- `contract/sample.taskbak` —— 正常样例（1 条带按钮、1 条循环）。
- `contract/real_export.taskbak` —— 从真机 `worknote.db` 转出来的真实数据（可作回归样本）。
- `contract/selftest/bad/*.taskbak` —— 5 个故意写坏的样本，用来证明校验器真的会拦（缺必填、枚举错、日期不存在、版本号错、按钮超长）。

## 七、版本演进规则

- `version` 现在是 `1`，**不轻易动**。
- 只加可选字段 = 不升版本，老客户端忽略即可。
- 改字段含义、删字段、改枚举值 = 升到 `2`，并且新端必须能读 `1`（迁移在读取时做，不要求用户重新导出）。
- 各端写文件时永远写**自己能写的最新版本**，读的时候按 `version` 分支。

## 附：这份契约管不到的东西（各端必须自己解决，别指望统一）

| 能力 | Android 现状 | iOS 的现实 | 鸿蒙 Next 的现实 |
| ---- | ---- | ---- | ---- |
| "不处理就关不掉"的强提醒 | 前台服务 + `TYPE_APPLICATION_OVERLAY` 悬浮卡片；无浮窗权限时退化成全屏 Activity | **系统不允许**：iOS 无法阻止用户划掉通知，也无法长期置顶浮层。只能做 Time Sensitive 通知（可穿透专注模式）+ 连续补发，把"关不掉"降级成"催得勤" | 有悬浮窗权限 `SYSTEM_FLOAT_WINDOW` 与通知，但能否常驻需实机/模拟器验证；系统对后台拉起限制比 Android 严 |
| 精确到点触发 | `AlarmManager` + `setExactAndAllowWhileIdle` | 本地通知 `UNCalendarNotificationTrigger`，误差由系统决定，不能保证秒级 | `reminderAgent` / `agent-powered reminder`，需验证后台保活 |
| 背景图三 Tab | 已实现（Activity 外壳铺图 + 虚化缓存） | SwiftUI 里给根容器铺图即可，天然共用 | ArkUI 用 `Stack` 根容器铺图，同样天然共用 |

**iOS 这条必须在开工前定下来**：产品卖点"不处理就关不掉的强提醒"在 iOS 上物理不可实现。可选做法是（a）接受降级为高频催办的通知，文案里说清楚"iOS 版提醒强度弱于 Android"；（b）iOS 版只做记录 + 普通提醒，不宣传强提醒。这个决定会影响 iOS 版的所有页面文案与商店外分发说明。
